| D-76 | 2026-11-10 | **How D-72 is enforced: row policy on `accounts_user` + a restricted view, not column grants.** The `accounts_user` SELECT policy for `travel_app` now allows only the account itself (while active, D-53), the Admin, and the `auth` login context. Migration `accounts/0003_user_directory`. | Column grants are role-wide, so they can't give "self and Admin see the email, others don't": they would deny the user's own email too, and every ORM load of `User` (session auth, `/me`, the login lookup) would need deferred fields plus a SECURITY DEFINER getter. | D-77 | 2026-11-10 | **Rate limiter (T2, D-10): fixed windows counted by one atomic upsert on a dedicated autocommit connection.** `travel/core/ratelimit.py`: `hit(scope, identifier, Rate(limit, period))` runs `INSERT … ON CONFLICT (key, window_start) DO UPDATE SET count = count + 1 RETURNING count` on the `ratelimit` DB alias (same role as `default`, a test mirror of it); `enforce` raises `RateLimited` (the API answers 429 + `Retry-After`); `limit(...)` is a view decorator keyed by client IP by default. Keys are `scope:` + HMAC-SHA256 of the identifier under the secret key; scopes must be lower-case words. Periods ≤ 1 day; an hourly Procrastinate task deletes windows that started over a day ago. `client_ip` uses the socket address unless `RATELIMIT_CLIENT_IP_HEADER` names a proxy header (only when every request comes through that proxy); IPv6 is grouped by /64. | Counting inside the request's transaction would hold each bucket's row lock until the request ends (serializing same-key requests and risking deadlocks between buckets) and would lose counts when a request rolls back. A second connection per web thread (≤ 8 more, under `max_connections = 60`) avoids both. The upsert serializes same-key writers on the row lock, so no increment is lost; a test with 12 real parallel connections proves it and fails against a read-then-write version. HMAC rather than plain SHA-256 because the IPv4 space is small enough to reverse a plain hash from a backup. |
